# Findings from building the platform with LearnKit

Using the library for a real site is the best test of it. What turned up, and what was done:

| Finding | What happened | Status |
| --- | --- | --- |
| Site CSS beats LearnKit's layers | A site-wide `a { color: ... }` rule turned the text of an `<a class="lk-button">` the same colour as its background. LearnKit is in cascade layers, so any ordinary CSS wins, by design. | Site CSS now excludes `.lk-button`. Worth a line in the theming guide. |
| Stepper fell apart with many steps | An 11-step process with long step names squashed every label into a one-letter column. | Fixed in the library on the `learnkit` branch: it now goes compact above five steps. |
| Transitions made a colour check misreport | The accessibility checks reported 1.12:1 text on a selected tile in dark mode. The tile was fine: the background transition had not advanced because nothing was being painted. | Checks now switch transitions off first. Worth remembering for any automated colour test. |
| Heading levels clashed with the page | A grid on the gallery page opened a level 3 heading straight after the page's level 1. Components take a `level` attribute so the page can fit them in; I had not set it correctly. | Fixed on the page. The checks now catch a skipped heading level anywhere. |
| The interactive states are where problems hide | The static pages passed every check. Only after answering quizzes and opening tiles did the checks find anything, and both findings were about the checks themselves. | Checks run before and after use. |
| HoW Digital's identity cannot be expressed yet | It uses bright accents as fills with dark text, and forbids them as text colours. LearnKit has one `primary` colour that does both jobs, so a faithful HoW theme needs a small contract extension (an accent fill and the text on it). | Not done. Recorded in the roadmap. |
| LearnKit has not been tried inside a Rise code block | The build account says the embed overrides the bare `hidden` attribute, which LearnKit uses widely. I added explicit rules for it, but this is untested. | Open. A test page now exists at `rise-test/` (paste it into a Rise code block or embed, press the buttons, send the report back). Do not put a component in a course until it has been run. |
| A sticky panel slid over the content below it | In the customiser, the preview was sticky and scrolled on its own, so the contrast section passed underneath it and the wheel got caught inside it. Found by the user, not by a test. | Fixed on `learnkit`, with a browser test that fails on the old layout. Lesson: a sticky element needs a parent that ends where it should stop, and nothing else in that parent. |
| A page's own link colour overrode the theme | Breadcrumb links failed contrast in every theme, but only inside the gallery. The gallery's unlayered `a { color }` beat LearnKit's layered rule. Found by scanning every new component in every theme and mode, not by reading the CSS. | Fixed in the gallery with `revert-layer`. Lesson: unlayered page CSS always wins, so a demo page must not style the things it demonstrates. |
| I described the reach check wrongly | Asked to swap the new `lk-flow` into "the reach check", I found the page had no decision tree. It is a diagnostic: four kinds of reach and five checks to try. I had called it "should I build this or use Rise?" without opening it. | Added the tree where a decision really fits: reading your own check results. Lesson: open the thing before proposing to change it. The "build or use Rise?" tree is still unbuilt. |
| Real content broke what the demo hid | The demo used short labels. The reach results were sentences, and the platform theme's very round corners clipped them inside the boxes. | Fixed in the library: corner rounding stops at 1rem, and an optional `data-detail` keeps long wording out of the chart. Lesson: try a component with real content, in the real theme, before calling it done. |
| A test passed while the thing it tested was wrong | In the walk-through the long result wording was meant to be hidden in the chart, but it was showing. My test checked the `hidden` attribute, and a `display: block` rule overrode it. Found by looking at the page, not by the test. | Fixed, and the test now measures what is rendered. Lesson: assert on what the learner sees, not on the attribute you set. |
| A chain of questions makes a wide chart | Each extra question in a tree adds a column, so four questions overflowed the page's width. | Cut the home page tree to three questions and narrowed the boxes. A stacked layout for narrow screens would fix it properly. Not built. |
| The site explained nothing to a newcomer | The home page of the library opened with "dependency-free", "no framework and no build step". The pages assumed words like theme, CSS and markup. A colleague with no developer background would meet all of them with no way to ask. | Every page now says what it is and what you can do on it, hints sit above the first quiz and journal, technical words link to a plain meaning, and tests keep it that way. Lesson: write for the least-informed reader first, then check the wording with a machine, because it drifts. |
